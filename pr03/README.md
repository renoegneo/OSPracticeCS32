# Практическая работа № 3. Процессы в Linux (вариант B)

Среда: Ubuntu (WSL2) на Windows 11, Python 3.12

## 1. ptree.py: дерево процессов по /proc

Скрипт обходит папки `/proc/<PID>`, читает `status` (поля `Name`, `State`, `PPid`, `Uid`, `VmRSS`), оставляет процессы текущего пользователя (по `Uid`) и строит дерево по `PPid`. Глубина вложенности показана отступами.

```
$ python3 ptree.py
355 systemd [S] RSS=11264 kB
  356 (sd-pam) [S] RSS=3516 kB
380 bash [S] RSS=4992 kB
501 bash [S] RSS=5120 kB
  897 python3 [R] RSS=10240 kB
```

Последний `python3` (PID 897) это сам `ptree.py`, дочерний процесс `bash` 501. Он в состоянии `R` (выполняется), остальные в `S` (спят в ожидании событий). Корнями дерева стали процессы, чьи родители принадлежат не мне (например, `/init`).

## 2. runner.py: N детей через fork + exec

Родитель N раз вызывает `os.fork()`. Каждый ребёнок через `os.execvp` заменяет себя переданной командой. Родитель в цикле `os.wait()` собирает всех детей и печатает код возврата и время работы. Если `exec` не удался (нет такой команды), ребёнок завершается с кодом 127.

```
$ python3 runner.py 3 sleep 2
PID=908 код=0 время=2.01 c
PID=907 код=0 время=2.03 c
PID=906 код=0 время=2.06 c

$ python3 runner.py 2 ls /нет/такого
ls: cannot access '/нет/такого': No such file or directory
ls: cannot access '/нет/такого': No such file or directory
PID=911 код=2 время=0.01 c
PID=910 код=2 время=0.01 c

$ python3 runner.py 2 nosuchcmd
PID=913 код=127 время=0.04 c
PID=914 код=127 время=0.04 c
```

Выводы:
- Три `sleep 2` отработали параллельно: каждый ~2 с, а не 2+4+6. PID в выводе идут не по порядку, потому что `wait()` возвращает детей в порядке завершения.
- `ls` на несуществующий путь вернул код 2, несуществующая команда даёт 127.

## 3. Зомби и сирота

### Зомби (zombie.py)

Ребёнок сразу делает `os._exit(0)`, а родитель 20 секунд спит и не вызывает `wait()`. Ядро хранит запись о завершившемся ребёнке (код возврата), пока родитель её не заберёт. Такой процесс и есть зомби.

```
$ python3 zombie.py &
Родитель PID=1037, ребёнок PID=1039 (станет зомби)
$ ps -o pid,ppid,stat,cmd --ppid $!
    PID    PPID STAT CMD
   1039    1037 Z    [python3] <defunct>
```

Состояние `Z`, команда `<defunct>`: процесс уже не выполняется и память не занимает, остаётся только строка в таблице процессов. Исчезает, когда родитель вызывает `wait()` или сам завершается (тогда зомби усыновляет другой процесс и сразу его «убирает»).

### Сирота (orphan.py)

Родитель печатает сообщение и сразу завершается, ребёнок живёт ещё 15 секунд.

```
$ python3 orphan.py
Родитель PID=978, ребёнок PID=979, родитель умирает
$ ps -eo pid,ppid,stat,cmd | grep '[o]rphan'
    979     497 S    python3 orphan.py
$ ps -p 497 -o pid,cmd
    PID CMD
    497 /init
```

У ребёнка 979 PPID был 978, после смерти родителя стал 497. Процесс 497 это `/init` (инициализирующий процесс WSL). В моей системе сироту усыновляет он, а не `systemd --user`: он выступает как subreaper (ближайший предок, который принимает осиротевших потомков и вызывает за них `wait()`), поэтому зомби из сирот не копятся.

## 4. Ленивое копирование памяти (copy-on-write)

После `fork` ядро не копирует память родителя: страницы остаются общими и копируются только при первой записи. Скрипт `cow.py` создаёт список из 3 000 000 чисел, делает `fork`, и в ребёнке измеряет память по `/proc/self/smaps_rollup` до и после изменения всех элементов списка.

```
$ python3 cow.py
Родитель до fork: RSS=124 МБ, Pss=120 МБ
Ребёнок сразу после fork: RSS=122 МБ, Pss=60 МБ
Ребёнок после изменения: RSS=122 МБ, Pss=118 МБ
```

Почему смотрю не только RSS: RSS считает все страницы, которые процесс видит в физической памяти, включая общие. Поэтому у ребёнка он сразу ≈ как у родителя (122 МБ) и после записи почти не меняется. Pss (proportional set size) делит каждую общую страницу поровну между владельцами:

Pss = личные страницы + общие страницы / число процессов, которые их делят.

- Сразу после fork почти всё общее между 2 процессами: 120 МБ / 2 = 60 МБ. Совпало с измерением (Pss=60).
- После изменения списка ребёнок получил собственные копии страниц, общего почти не осталось, Pss вернулся к ≈ 118 МБ.

Это и есть ленивое копирование: память физически дублируется только в момент записи.

## Контрольные вопросы

**Почему fork возвращает два разных значения?**
Вызывается `fork` один раз, но возвращается он дважды: в родителе и в ребёнке (два процесса продолжают выполнение с одной и той же точки). В ребёнке возвращается 0, в родителе PID ребёнка. По этому значению код понимает, в какой ветке он находится.

**Что изменится, если вызвать exec без предварительного fork?**
Текущий процесс заменит свой образ программой из `exec`: тот же PID, но код и данные другие, а всё, что написано после `exec`, не выполнится. Вызывающий процесс «исчезнет» (в оболочке это закрыло бы саму оболочку). Поэтому `exec` обычно вызывают в ребёнке после `fork`.
