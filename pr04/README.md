# Практическая работа № 4. Потоки (вариант B)

Среда: Ubuntu (WSL2) на Windows 11, Python 3. Число ядер (`nproc`): **12**. Число воркеров (потоков/процессов): 4. Каждое измерение повторено **3 раза**, в таблице **медиана** (среднее по значению из трёх времён: при 3 повторах это второе по величине, оно не искажается одним случайным выбросом).

Данные генерировались отдельным скриптом `gen_numbers.py` (10 млн целых чисел от 1 до 100, `seed=42`), в замеры генерация и чтение файла не входят.

## 1. Сумма 10 млн чисел

Сумма считается обычным циклом `for` (код Python), а не встроенной `sum()`: она написана на C и считает слишком быстро, накладные расходы потоков/процессов перекрыли бы разницу.

```
$ python3 sum_bench.py
1 поток    времена=[0.27, 0.23, 0.23] медиана=0.23 c
4 потока   времена=[0.24, 0.23, 0.21] медиана=0.23 c
4 процесса времена=[0.18, 0.1, 0.1] медиана=0.10 c
```

Результат каждого варианта сверялся с эталонной суммой (`assert`).

## 2. Сетевая задача (20 URL)

Вместо внешних сайтов использован локальный HTTP-сервер `server.py`, который отвечает на каждый запрос с задержкой 0.3 с (имитация сети). Сервер многопоточный, чтобы он сам не стал узким местом.

```
$ python3 server.py &
$ python3 net_bench.py
последовательно времена=[6.37, 6.32, 6.37] медиана=6.37 c
потоки         времена=[1.57, 1.56, 1.59] медиана=1.57 c
процессы       времена=[1.61, 1.6, 1.58] медиана=1.60 c
$ pkill -f server.py
```

## 3. Сводная таблица

(nproc = 12, воркеров = 4, повторов = 3, значение = медиана)

| Задача | Способ | Время, с | Ускорение |
|---|---|---|---|
| Сумма 10 млн чисел | 1 поток | 0.23 | 1.00 |
| Сумма 10 млн чисел | 4 потока (threading) | 0.23 | 1.00 |
| Сумма 10 млн чисел | 4 процесса (multiprocessing) | 0.10 | 2.30 |
| Загрузка 20 URL | последовательно | 6.37 | 1.00 |
| Загрузка 20 URL | ThreadPoolExecutor (4) | 1.57 | 4.06 |
| Загрузка 20 URL | ProcessPoolExecutor (4) | 1.60 | 3.98 |

Ускорение считается как S = T₁ / Tₚ, где T₁ время базового варианта (1 поток / последовательно), Tₚ время параллельного варианта. Подставляем:

- сумма, потоки: S = 0.23 / 0.23 = 1.00
- сумма, процессы: S = 0.23 / 0.10 = 2.30
- сеть, потоки: S = 6.37 / 1.57 ≈ 4.06
- сеть, процессы: S = 6.37 / 1.60 ≈ 3.98

Идеальное ускорение при 4 воркерах равно 4. Эффективность E = S / N, для процессов в счёте: E = 2.30 / 4 = 0.575 (57%), для сети с потоками: E = 4.06 / 4 ≈ 1.0 (101%, разница с идеалом в пределах погрешности измерения).

## 4. Потоки делят память, процессы нет

```
$ python3 shared.py
  внутри (поток): ['поток']
Родитель после потока: ['поток']
  внутри (процесс): ['поток', 'процесс']
Родитель после процесса: ['поток']
```

Поток изменил глобальный список, и родитель видит изменение: у потоков одно адресное пространство. Процесс получил при `fork` **копию** памяти родителя (поэтому внутри у него уже был элемент `'поток'`), дописал в свою копию, а список в родителе остался прежним.

## 5. Объяснение результатов (GIL)

**GIL** (Global Interpreter Lock) это замок в CPython: в каждый момент байт-код Python исполняет только один поток, даже если ядер много (у меня 12).

**Счёт: потоки не ускоряют.** Цикл суммирования целиком состоит из байт-кода Python, значит, всё время нужен GIL. 4 потока по очереди берут замок и не могут считать одновременно: 0.23 с против 0.23 с, ускорения нет (S = 1.00). Плюс небольшие потери на переключение.

**Счёт: процессы ускоряют.** У каждого процесса свой интерпретатор и свой GIL, поэтому 4 процесса реально считают на 4 разных ядрах одновременно: 0.23 → 0.10 с.

**Почему не в 4 раза (S = 2.30, а не 4).** Процессы дороже:
- нужно создать пул и запустить 4 процесса (`fork`), это входит в замер;
- нужно вернуть результаты родителю через pickle (сериализацию);
- сама работа очень короткая (0.23 с), поэтому фиксированные накладные расходы составляют заметную долю. Первый запуск процессов был заметно медленнее двух следующих (0.18 против 0.10 с), вероятно, из-за «холодного» старта.

Для более длинной задачи доля накладных расходов упала бы, и ускорение приблизилось бы к 4.

**Ввод-вывод: потоки помогают.** Во время ожидания ответа сервера поток находится в системном вызове и **отпускает GIL**, пока ждёт сеть. Пока один поток ждёт, остальные отправляют свои запросы. Проверка по формулам:
- последовательно: 20 запросов × 0.3 с = 6.0 с (измерено 6.37, остальные ~0.37 с это накладные расходы на соединения);
- 4 потока: 20 / 4 = 5 «волн» по 0.3 с = 1.5 с (измерено 1.57).

Ускорение 6.37 / 1.57 ≈ 4 это почти ровно число потоков.

**Ввод-вывод: процессы тоже помогают, но дороже.** 1.60 с против 1.57 с у потоков: тот же выигрыш, но чуть медленнее из-за запуска процессов и передачи результатов. На потоках эта цена не платится, они лёгкие.

## 6. Когда что использовать

- **Потоки**: задача упирается в ожидание (сеть, диск, БД). Дёшево, общая память, GIL при ожидании не мешает.
- **Процессы**: задача упирается в вычисления на CPU (счёт на чистом Python). Обходят GIL и используют несколько ядер, но дороже: запуск, отдельная память, обмен данными только через сериализацию.
- **Короткие задачи** не стоит параллелить совсем: накладные расходы могут съесть выигрыш (в расчётах выше процессы дали лишь 2.3× из 4×).

## Контрольные вопросы

**1. Что общего у потоков одного процесса и что у каждого своё?**
Общее: адресное пространство (код, куча, глобальные переменные), открытые файлы и дескрипторы, PID. У каждого потока своё: стек вызовов, значения регистров (в том числе счётчик команд), идентификатор потока (TID) и состояние (работает/ждёт). Подтверждено в `shared.py`: изменение глобального списка в потоке видно родителю.

**2. Почему в CPython 4 потока не ускорили счёт, а 4 процесса ускорили?**
Из-за GIL потоки одного процесса не могут одновременно исполнять байт-код Python, поэтому счёт идёт по очереди (0.23 с против 0.23 с). У каждого процесса свой интерпретатор и свой GIL, поэтому они считают параллельно на разных ядрах (0.23 → 0.10 с). Ускорение меньше идеального из-за накладных расходов на создание процессов и передачу результатов.
