## Неточности задания и принятые решения

1. **«1000 элементов»** — понимаю как 1000 всего. 1000 не делится на 3, поэтому производитель `pid` выдаёт `range(pid, 1000, 3)`:
   - pid=0: 0, 3, …, 999 → (999−0)/3 + 1 = **334**
   - pid=1: 1, 4, …, 997 → (997−1)/3 + 1 = **333**
   - pid=2: 2, 5, …, 998 → (998−2)/3 + 1 = **333**
   - итого 334 + 333 + 333 = **1000**, номера не пересекаются.
2. **Завершение потребителей** задание не описывает. Решение (моё): после `join` производителей кладём в буфер 2 значения `STOP = -1`, по одному на потребителя («ядовитые таблетки»). Всего в буфер уходит 1000 + 2 = 1002 `put`.
3. **«Потерянное пробуждение» в п.4 названо неточно.** То, что ломается при `if` вместо `while`, называется «украденное/лишнее пробуждение» (поток проснулся, а условие снова ложно). Настоящее потерянное пробуждение — это `notify` до `wait`, когда сигнал уходит в пустоту. Лечатся оба случая одним приёмом: проверкой условия в `while`.
4. **GIL** (глобальная блокировка интерпретатора CPython) делает гонки редкими, поэтому в сломанных версиях окно гонки расширено паузой `RACE_DELAY = 0.0001` с.

## 1. Производитель–потребитель (3 производителя, 2 потребителя, буфер на 5)

Кольцевой буфер: `head` (откуда читаем), `tail` (куда пишем), `count`; индекс замыкается операцией `% 5`. Инвариант: `0 ≤ count ≤ 5`. Нарушения не роняют программу, а пишутся в список `violations`.

### (а) 2 семафора + мьютекс

- `empty = Semaphore(5)` — число свободных слотов, `full = Semaphore(0)` — число занятых, `mutex` защищает `head/tail/count`.
- `put`: `empty.acquire()` → `with mutex: запись` → `full.release()`. `get` симметрично.
- **Порядок важен:** сначала семафор, потом мьютекс. Если наоборот, производитель возьмёт мьютекс и уснёт на `empty`, а потребитель не войдёт за мьютексом, чтобы освободить место, и получится взаимная блокировка (deadlock).

```
=== (а) 2 семафора + мьютекс ===
время:            0.050 с
потреблено всего: 1000 (потребитель 0: 567, потребитель 1: 433)
дубликатов:       0
потеряно:         0
нарушений буфера: 0
буфер в конце:    count=0
зависших потоков: 0
РЕЗУЛЬТАТ: OK
```

### (б) Мьютекс + условные переменные

- Один мьютекс и две условные переменные на нём: `not_full` («есть место») и `not_empty` («есть элемент»). Каждая будит только «своих» ждущих.
- `wait()` атомарно отпускает мьютекс и засыпает, при пробуждении берёт мьютекс обратно. Условие проверяется в `while`.

```
=== (б) мьютекс + условные переменные ===
время:            0.033 с
потреблено всего: 1000 (потребитель 0: 496, потребитель 1: 504)
дубликатов:       0
потеряно:         0
нарушений буфера: 0
буфер в конце:    count=0
зависших потоков: 0
РЕЗУЛЬТАТ: OK
```

### Повторные прогоны

- По 5 запусков каждой версии: 10 из 10 `РЕЗУЛЬТАТ: OK`.
- Со случайными паузами `JITTER = 0.0005` с (потоки чередуются разнообразнее — проверка жёстче):

```
=== sem, JITTER=0.0005 ===   время: 0.221 с   дубликатов: 0   потеряно: 0   нарушений: 0   РЕЗУЛЬТАТ: OK
=== cond, JITTER=0.0005 ===  время: 0.212 с   дубликатов: 0   потеряно: 0   нарушений: 0   РЕЗУЛЬТАТ: OK
```

Время одного запуска — не бенчмарк: разница 0,050 против 0,033 с лежит в пределах разброса, делать вывод «какая версия быстрее» по ней нельзя.

Размер критических секций минимален: под мьютексом только `_put_raw`/`_get_raw`. Ожидание (`acquire`/`wait`) происходит вне захваченной секции или с её отпусканием (типичная ошибка «слишком широкая секция» не допущена).

## 2. Проверка корректности

Проверки сделаны кодом, а не «на глаз», и считаются в главном потоке после `join`:
- **«Ровно один раз»:** каждый потребитель пишет в свой список; после `join` собираем всё в `Counter` и ищем значения с счётчиком > 1 (дубликаты) и числа из `range(1000)`, которых нет (потери).
- **«Буфер не переполняется»:** `_put_raw` при `count >= 5` и `_get_raw` при `count <= 0` пишут строку в `violations`; в конце ещё проверяем `count == 0`.
- Зависшие потоки ловим через `join(timeout)` + `is_alive()`.

### Проверка проверяющего: версия с гонкой `pc_nomutex.py`

Семафоры оставлены, мьютекс убран. Два производителя могут прочитать один и тот же `tail` и записать в один слот; `count += 1` — не атомарная операция (прочитать, прибавить, записать).

```
=== БЕЗ мьютекса (сломано) ===            (1-й запуск)
время:            10.122 с
потреблено всего: 1001 (потребитель 0: 500, потребитель 1: 501)
дубликатов:       387
   примеры: [(1, 2), (6, 2), (2, 2), (9, 2), (10, 2)]
потеряно:         486
   примеры: [3, 4, 5, 7, 8]
нарушений буфера: 0
буфер в конце:    count=0
зависших потоков: 1 ['C0']
РЕЗУЛЬТАТ: FAIL

=== БЕЗ мьютекса (сломано) ===            (2-й запуск)
время:            0.104 с
потреблено всего: 1000 (потребитель 0: 499, потребитель 1: 501)
дубликатов:       386
   примеры: [(0, 2), (1, 2), (6, 2), (9, 2), (8, 2)]
потеряно:         501
   примеры: [2, 3, 4, 5, 7]
нарушений буфера: 0
буфер в конце:    count=0
зависших потоков: 0
РЕЗУЛЬТАТ: FAIL
```

Наблюдения:
- Арифметика 2-го запуска: потреблено 1000 = 499 уникальных + 501 лишняя копия; потеряно 1000 − 499 = 501. Лишних копий ровно столько, сколько потерянных. Пример `(1, 2)` значит «значение 1 прочитано дважды».
- В 1-м запуске прочитано 1001 (на одно больше), поэтому лишних копий 1001 − 514 = 487 против 486 потерянных.
- «Нарушений буфера: 0» и `count=0` в конце: семафоры защищают от переполнения и чтения пустого буфера, но **не защищают содержимое слотов**. Портится не `count`, а данные. Значит, проверка одной лишь «вместимости» гонку бы не поймала, нужна проверка «ровно один раз».
- Зависание `C0` и время 10,122 с (сработал `TIMEOUT = 10` с) — вероятно, гонка повредила один из `STOP`, и потребитель остался ждать на `full`. Точный сценарий по шагам я не разбирал, это гипотеза.

## 3. Барьер на условной переменной (4 потока, 3 фазы)

Барьер хранит `count` (сколько потоков пришло), `generation` (номер поколения) и условную переменную. Последний пришедший поток сбрасывает `count`, увеличивает `generation` и делает `notify_all()`; остальные ждут `while gen == self.generation`.

**Зачем `generation`:** быстрый поток, пройдя барьер, сразу придёт на него снова (следующая фаза). Условие «count == n» к этому моменту уже сброшено, и спящие потоки могли бы не заметить, что барьер открывался. Номер поколения не сбрасывается, поэтому «открылся» не теряется. Цикл `while` защищает ещё и от ложных пробуждений.

Инвариант (проверяется кодом по журналу событий): ни один поток не начал фазу k+1, пока не закончили **все** потоки фазы k.

Фрагмент журнала `barrier.py` (фазы 0 → 1):

```
[ 4] W1 end   фаза 0
[ 5] W0 end   фаза 0
[ 6] W3 end   фаза 0
[ 7] W2 end   фаза 0
[ 8] W2 start фаза 1
```

Все четыре `end` фазы 0 (события 4–7) идут раньше первого `start` фазы 1 (событие 8); так же между фазами 1 и 2 (события 12–15, затем 16). Итог: `зависших потоков: 0`, `РЕЗУЛЬТАТ: OK`.

Версия с гонкой `barrier_broken.py` (`wait()` ничего не делает) проверкой поймана:

```
НАРУШЕНИЕ: фаза 1 началась (событие #5) раньше, чем закончилась фаза 0 (событие #13)
НАРУШЕНИЕ: фаза 2 началась (событие #7) раньше, чем закончилась фаза 1 (событие #20)
РЕЗУЛЬТАТ: FAIL
```

## 4. `if` вместо `while` вокруг `wait`

Сценарий управляемый: два потребителя ждут на условной переменной, производитель кладёт **один** элемент и будит **обоих** (`notify_all`).

`python3 wakeup.py if` (сломано):

```
P: положил 1, notify_all()
C1: проснулся, items=[1]
C1: взял 1
C2: проснулся, items=[]
C2: НАРУШЕНИЕ — данных нет, а я иду их забирать
P: положил 2, notify_all()
осталось в items: [2]; зависших потоков: 0
```

`python3 wakeup.py while` (правильно):

```
P: положил 1, notify_all()
C2: проснулся, items=[1]
C2: взял 1
P: положил 2, notify_all()
C1: проснулся, items=[2]
C1: взял 2
осталось в items: []; зависших потоков: 0
```

(Какой из C1/C2 успеет первым, меняется от запуска к запуску, это нормально.)

**При каком чередовании ломается `if`:**
1. C1 и C2 проверили `if not items` (пусто) и уснули в `wait()`.
2. P кладёт 1 элемент и делает `notify_all()` — просыпаются оба, но мьютекс достаётся им по очереди.
3. C1 берёт мьютекс, забирает элемент, отпускает мьютекс.
4. C2 берёт мьютекс. С `if` условие уже не проверяется (оно было проверено до сна), C2 идёт забирать данные из пустого списка. В буфере это было бы чтение из пустого: `count` уйдёт в −1.
5. С `while` C2 после пробуждения перепроверяет `items`, видит пустоту и засыпает снова.

Тот же эффект («украденное пробуждение») даёт и одиночный `notify`: между пробуждением C1 и получением им мьютекса в критическую секцию может зайти *новый* поток, который не спал, и забрать элемент. Кроме того, стандарты (POSIX) допускают ложные пробуждения без всякого `notify`. Правило одно: условие ждём в цикле `while`, а не в `if`.

**Потерянное пробуждение** (термин в строгом смысле): `notify` вызван раньше, чем поток начал ждать, и сигнал никто не получил. Условная переменная сигналы не запоминает (в отличие от семафора, у которого есть счётчик). Лечится тем, что условие хранится в общей переменной и проверяется под мьютексом перед `wait`.

## Ответы на контрольные вопросы

**1. Чем семафор со значением 1 отличается от мьютекса на практике?**
- У мьютекса есть владелец: в POSIX (`pthread_mutex_t`) разблокировать его должен тот же поток, что захватил. Семафор «владельца» не имеет: `release()` может вызвать любой поток, поэтому семафор годится для **сигнализации** между потоками (так `full`/`empty` в п.1(а): производитель делает `release`, а
