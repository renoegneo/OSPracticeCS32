## 4. Реализация

### 4.1. Клиент-сервер на FIFO

Для обмена данными используются два именованных канала:

- `/tmp/pr07_req` — передача запросов от клиента серверу.
- `/tmp/pr07_resp` — передача ответов от сервера клиенту.

Клиент отправляет арифметические выражения, сервер вычисляет их и возвращает результат. Проверяются обычные арифметические операции, скобки, деление, остаток от деления, обработка ошибок и недопустимые выражения.

**Результаты проверки:**
- Все 9 эталонных тестов прошли успешно.
- Выполнены три последовательных запуска клиентов.
- Дополнительно проверены выражения `2+2`, `3*(4+1)` и `5/0`.
- Все клиенты завершились с кодом возврата `0`.

FIFO блокирует открытие на чтение или запись, пока другой процесс не откроет соответствующий конец канала. Это штатное поведение, а не зависание. Поэтому сервер и клиент должны согласованно открывать каналы.

В данной реализации клиенты запускаются строго по очереди. Два общих FIFO не обеспечивают отдельную маршрутизацию ответов для нескольких одновременно работающих клиентов.

### 4.2. Клиент-сервер на Unix domain sockets

Сервер использует `socket.AF_UNIX` и `socket.SOCK_STREAM`. Для обслуживания каждого подключившегося клиента создаётся отдельный поток. Клиенты запускаются в отдельных процессах с помощью `multiprocessing`.

Каждый клиент отправлял пять запросов с паузой 0,2 секунды между ними. При последовательном обслуживании ожидаемое время составляло около 4 секунд для четырёх клиентов и 8 секунд для восьми. Фактически оба теста заняли около 1,09 секунды.

Перемешивание сообщений от разных клиентов и близкое время выполнения подтверждают, что сервер обслуживал клиентов параллельно.

### 4.4. Сравнение механизмов передачи данных

В `bench_ipc.py` сравниваются четыре механизма:

1. `Pipe` — однонаправленный канал между процессами.
2. FIFO — именованный канал в файловой системе.
3. Unix domain socket — локальный потоковый сокет.
4. `shared_memory` — разделяемая память.

Для эксперимента использовался массив из \(10^7\) целых чисел типа `int64`. Размер данных составляет **80 000 000 байт, или 80 МБ**.

Каждый механизм тестировался три раза. Для сравнения использована медиана трёх замеров. Контрольная сумма SHA-256 вычислялась вне измеряемого интервала. Во всех прогонах данные совпали с исходными.

Скорость передачи рассчитывается по формуле:

\[
V = \frac{80\,000\,000}{t \cdot 1\,000\,000}
\]

где \(t\) — время в секундах, а \(V\) — скорость в МБ/с.

### 4.5. Результаты замеров

| Механизм | Медианное время | Скорость передачи |
|---|---:|---:|
| Pipe (`os.pipe`) | 0,203 с | 395 МБ/с |
| FIFO (`mkfifo`) | 0,105 с | 760 МБ/с |
| Unix-сокет (`AF_UNIX`) | 0,023 с | 3552 МБ/с |
| `shared_memory` | 0,059 с | 1359 МБ/с |

**Результат бенчмарка: `OK`.** Все 12 прогонов завершились успешно: четыре механизма по три прогона каждый.

В данном эксперименте наибольшая измеренная скорость получена у Unix domain socket — 3552 МБ/с. Далее идут разделяемая память, FIFO и обычный pipe.

Эти значения относятся к конкретному тесту и среде выполнения. Они не означают, что Unix domain sockets всегда быстрее остальных механизмов: результат зависит от реализации, размера буферов, способа чтения и записи, планирования процессов и методики измерения.

**Ограничение измерения:** для `shared_memory` замер включает создание сегмента, копирование данных в него и подключение принимающего процесса. Однако принимающий процесс сообщает о получении данных до вычисления SHA-256, то есть время не включает полное чтение всего массива принимающим процессом. Поэтому полученные значения полезны для сравнения реализаций в данном тесте, но не являются полностью равнозначным измерением сквозной передачи данных.

## 5. Особенности синхронизации и передачи данных

**Pipe и FIFO.** Передача выполняется через буферы ядра. Для корректной работы важно закрывать неиспользуемые концы каналов, согласованно открывать FIFO и корректно обрабатывать завершение потока данных.

**Unix domain sockets.** Сокеты позволяют организовать отдельное соединение с каждым клиентом. Сервер может обрабатывать несколько соединений параллельно, но приложению необходимо соблюдать протокол обмена сообщениями.

**Разделяемая память.** Оба процесса получают доступ к одной области памяти, поэтому весь массив не требуется передавать через канал ядра. При этом готовность данных не определяется автоматически: необходима синхронизация. В данной реализации используется `multiprocessing.Event`.

SHA-256 используется для проверки целостности переданных данных. Во всех прогонах бенчмарка контрольные суммы совпали.

## 7. Ответы на контрольные вопросы

**1. Почему разделяемая память считается самым быстрым и самым опасным механизмом IPC?**

Разделяемая память позволяет нескольким процессам обращаться к одной области памяти без постоянного копирования всего массива через буферы ядра. Это может обеспечить высокую производительность при передаче больших объёмов данных.

Однако синхронизация доступа не выполняется автоматически. Если один процесс читает данные до окончания записи или несколько процессов одновременно изменяют одну область памяти, возникают гонки данных и непредсказуемые результаты.

**2. Что произойдёт при записи в pipe, у которого закрыты все читающие концы?**

В Python запись обычно приводит к исключению `BrokenPipeError`. На уровне ОС при попытке записи в такой pipe генерируется сигнал `SIGPIPE`; если он не обработан или не игнорируется, процесс может завершиться.
