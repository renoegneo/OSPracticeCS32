## 1. Алгоритм банкира

Формат входа: строка `available`, затем по строке на процесс (PID, Allocation, Max). Запросы читаются из stdin строками `PID вектор`. Need = Max − Allocation.

**Проверка безопасности:** Work = Available; ищем процесс, у которого Need ≤ Work; считаем, что он завершился и вернул всё, что держал (Work += Allocation), и повторяем. Если завершились все, состояние безопасное.

**Запрос:** сначала проверка Request ≤ Need (иначе ERROR), затем Request ≤ Available (иначе WAIT); потом пробное выделение, проверка безопасности и, если состояние небезопасно, откат (возврат ресурсов).

### bank1.txt (безопасное состояние)

```
$ python3 banker.py bank1.txt < /dev/null
Available: [3, 3, 2]
P0: Allocation=[0, 1, 0] Max=[7, 5, 3] Need=[7, 4, 3]
P1: Allocation=[2, 0, 0] Max=[3, 2, 2] Need=[1, 2, 2]
P2: Allocation=[3, 0, 2] Max=[9, 0, 2] Need=[6, 0, 0]
P3: Allocation=[2, 1, 1] Max=[2, 2, 2] Need=[0, 1, 1]
P4: Allocation=[0, 0, 2] Max=[4, 3, 3] Need=[4, 3, 1]
Начальное состояние: SAFE  P1 -> P3 -> P4 -> P0 -> P2
```

Программа выдала последовательность `P1, P3, P4, P0, P2` (как в учебнике). В условии указана `P1, P3, P4, P2, P0`. Безопасных последовательностей может быть несколько, какая выйдет, зависит от порядка перебора. Проверим вручную, что последовательность из условия тоже допустима (Work начинается с Available = (3, 3, 2)):

| Шаг | Процесс | Need | Need ≤ Work? | Work после (Work + Allocation) |
|---|---|---|---|---|
| 1 | P1 | (1, 2, 2) | (1,2,2) ≤ (3,3,2) да | (3,3,2) + (2,0,0) = (5,3,2) |
| 2 | P3 | (0, 1, 1) | (0,1,1) ≤ (5,3,2) да | (5,3,2) + (2,1,1) = (7,4,3) |
| 3 | P4 | (4, 3, 1) | (4,3,1) ≤ (7,4,3) да | (7,4,3) + (0,0,2) = (7,4,5) |
| 4 | P2 | (6, 0, 0) | (6,0,0) ≤ (7,4,5) да | (7,4,5) + (3,0,2) = (10,4,7) |
| 5 | P0 | (7, 4, 3) | (7,4,3) ≤ (10,4,7) да | (10,4,7) + (0,1,0) = (10,5,7) |

Все пять процессов завершились, а итоговый Work (10, 5, 7) равен общему числу ресурсов (сумма Allocation (7, 2, 5) плюс Available (3, 3, 2)). Значит, последовательность из условия допустима, и оба порядка подтверждают, что состояние безопасно.

### bank2.txt (небезопасное состояние)

```
$ python3 banker.py bank2.txt < /dev/null
Available: [0, 1, 0]
(таблица Allocation/Max/Need та же)
Начальное состояние: UNSAFE
```

Почему: Work = (0, 1, 0), и ни у одного процесса Need не помещается: P0 (7,4,3), P1 (1,2,2: 1 > 0 по A), P2 (6,0,0), P3 (0,1,1: 1 > 0 по C), P4 (4,3,1). Ни один не может даже начать завершаться, значит безопасной последовательности нет.

### Запросы на bank1

```
$ printf 'P1 1 0 2\nP4 3 3 0\nP0 0 2 0\nP2 0 1 0\n' | python3 banker.py bank1.txt
request P1 [1, 0, 2]: GRANTED (безопасная последовательность: P1 -> P3 -> P4 -> P0 -> P2)
request P4 [3, 3, 0]: WAIT (ресурсов сейчас нет: Request > Available)
request P0 [0, 2, 0]: DENIED (состояние стало бы небезопасным, выполнен откат)
request P2 [0, 1, 0]: ERROR (запрос превышает заявленный максимум: Request > Need)
```

Состояние меняется последовательно, разбор:

1. **P1 (1, 0, 2):** (1,0,2) ≤ Need (1,2,2) и ≤ Available (3,3,2). После выделения Available = (2,3,0), Allocation P1 = (3,0,2), Need P1 = (0,2,0). Безопасность проверена (цепочка та же), запрос одобрен.
2. **P4 (3, 3, 0):** (3,3,0) ≤ Need P4 (4,3,1), но Available теперь (2,3,0), и 3 > 2 по A. Процесс должен ждать (WAIT), состояние не меняется.
3. **P0 (0, 2, 0):** (0,2,0) ≤ Need P0 (7,4,3) и ≤ Available (2,3,0). Пробное выделение даёт Available = (2,1,0), Allocation P0 = (0,3,0), Need P0 = (7,2,3). Проверка: Work = (2,1,0); P0 (7,2,3) нет; P1 (0,2,0): 2 > 1 по B, нет; P2 (6,0,0) нет; P3 (0,1,1): 1 > 0 по C, нет; P4 (4,3,1) нет. Никто не может завершиться, состояние небезопасно, запрос отклонён с откатом, хотя ресурсы физически были.
4. **P2 (0, 1, 0):** Need P2 = (6,0,0), а 1 > 0 по B: процесс просит больше, чем заявил в Max. Ошибка.

## 2. Детектор взаимоблокировок по журналу событий

Журнал: строки `acquire поток ресурс`, `release поток ресурс`, `wait поток ресурс`. После каждого события строится **граф ожидания** (не граф распределения): ребро `A → B` значит «поток A ждёт ресурс, которым владеет поток B». Цикл ищется обходом в глубину (DFS): вершины красятся «белый, серый, чёрный», и если из вершины идём в «серую» (она уже на текущем пути), цикл найден; участники это часть пути от этой вершины.

```
$ python3 waitgraph.py events_deadlock.log
Событие 6 (wait T2 A): ВЗАИМОБЛОКИРОВКА
  T3 ждёт A, им владеет T1
  T1 ждёт B, им владеет T2
  T2 ждёт A, им владеет T1
Участники цикла: T1 -> T2 -> T1

$ python3 waitgraph.py events_ok.log
Взаимоблокировки нет
```

Рёбра графа на шестом событии: T3 → T1, T1 → T2, T2 → T1. До события 6 был только путь T3 → T1 → T2 без цикла (T2 ещё ничего не ждал). Шестое событие замкнуло T2 → T1, и цикл появился. Поток T3 тоже заблокирован, но **не участвует в цикле**: он ждёт T1, а T1 сам застрял. Поэтому в «Участниках» только T1 и T2. Граф распределения ресурсов (с ресурсами как вершинами) дал бы ложные срабатывания, поэтому строится именно граф ожидания.

## 3. Программа с взаимоблокировкой и TrackedLock

### Как убедиться, что deadlock.py зависает

`deadlock.py` приложен без изменений (из задания). Два потока берут `lock_a` и `lock_b` в разном порядке. Строка `faulthandler.dump_traceback_later(5, exit=True)` через 5 с печатает стеки всех потоков и завершает программу.

```
$ python3 deadlock.py; echo "код выхода: $?"
T1 взял А, жду В
T2 взял В, жду А
Timeout (0:00:05)!
Thread 0x...6c0 (most recent call first):
  File ".../deadlock.py", line 21 in worker2
  ...
Thread 0x...6c0 (most recent call first):
  File ".../deadlock.py", line 14 in worker1
  ...
Thread 0x...080 (most recent call first):
  File ".../threading.py", line 1147 in join
  File ".../deadlock.py", line 27 in <module>
код выхода: 1
```

Признаки зависания: после двух сообщений программа молчит 5 секунд, строки `готово` нет, сработал таймаут (код выхода 1). Дамп показывает, где ждёт каждый поток: `worker1` на строке 14 (`with lock_b`, ждёт B, которым владеет worker2), `worker2` на строке 21 (`with lock_a`, ждёт A, которым владеет worker1), а главный поток ждёт их обоих в `join` (строка 27).

Нарушенное условие из четырёх (Коффмана): **циклическое ожидание**: T1 держит A и ждёт B, T2 держит B и ждёт A. Остальные три условия (взаимное исключение, удержание и ожидание, отсутствие принудительного освобождения) выполняются у любых обычных замков.

### TrackedLock

Обёртка над `threading.Lock`. Перед блокирующим `acquire` поток записывает «я жду этот замок» в общую таблицу, из таблиц строится граф ожидания (поток → владелец замка, которого он ждёт), и та же функция `find_cycle` ищет цикл. Если запрос замкнул цикл, бросается `DeadlockError`, а поток не блокируется. Таблицы защищены отдельным замком `_guard`; при `release` владелец снимается до разблокировки замка, иначе можно стереть запись следующего владельца.

```
$ python3 deadlock_tracked.py
T1 взял A, жду B
T2 взял B, жду A
T2: T2 запросил замок A; цикл ожидания: T1 -> T2 -> T1
T1 взял A и B
готово
```

Тот же сценарий, что в `deadlock.py`, завершился (есть `готово`, нет `Timeout`). Поток T2 получил исключение, при выходе из `with` отпустил B, и T1 доработал. Какой поток получит исключение, зависит от гонки: им становится тот, кто вторым запросит замок и замкнёт цикл (здесь T2).

## 4. Обедающие философы

5 философов, 5 вилок (замков). Цикл философа: думает (до 0.01 с) → берёт первую вилку → пауза 0.02 с → берёт вторую → ест 0.05 с → кладёт обе. Пауза между вилками оставлена во всех режимах: исправления должны работать вопреки ей. Опыт длится 5 с.

- **naive:** сначала левая вилка, потом правая. Если все пятеро взяли левую, каждый ждёт правую (чужую левую): круговое ожидание.
- **ordered (нумерация вилок):** всегда сначала вилка с меньшим номером. Философ 4 (вилки 4 и 0) берёт сначала вилку 0.
- **limited (ограничение):** за стол допускаются не более N − 1 = 4 философов (семафор). Пятерым вилок хватит всегда: хотя бы один получит обе.

```
$ python3 philosophers.py naive
режим=naive: за 5 с поели [0, 0, 0, 0, 0], всего 0
ЗАВИСЛИ философы: [0, 1, 2, 3, 4]
$ python3 philosophers.py ordered
режим=ordered: за 5 с поели [19, 37, 37, 37, 19], всего 149
ЗАВИСЛИ философы: нет
$ python3 philosophers.py limited
режим=limited: за 5 с поели [20, 20, 20, 21, 21], всего 102
ЗАВИСЛИ философы: нет
```

| Режим | Поели (P0…P4) | Всего | Разброс (мин–макс) | Зависли |
|---|---|---|---|---|
| naive | 0, 0, 0, 0, 0 | 0 | 0–0 | все 5 |
| ordered | 19, 37, 37, 37, 19 | 149 | 19–37 | нет |
| limited | 20, 20, 20, 21, 21 | 102 | 20–21 | нет |

(По одному запуску на режим; параметры N = 5, THINK ≤ 0.01 с, PAUSE = 0.02 с, EAT = 0.05 с, DURATION = 5 с.)

Выводы:

- **naive** взаимоблокируется сразу: все пятеро успевают взять левую вилку за время думания (до 0.01 с), раньше, чем кто-то закончит паузу в 0.02 с, и ждут друг друга по кругу. Ни один не поел ни разу.
- **Оба исправления снимают взаимоблокировку, но по-разному делят стол.** Сколько философов в среднем едят одновременно: суммарное время еды = число приёмов × 0.05 с, делим на длительность опыта 5 с. Для ordered: 149 · 0.05 / 5 = 1.49, для limited: 102 · 0.05 / 5 = 1.02. Теоретический максимум 2 (каждому нужно 2 вилки из 5, ⌊5 / 2⌋ = 2).
- **ordered** использует стол лучше (в среднем 1.49 едока, всего 149 приёмов), но **несправедлив**: философы 0 и 4 поели по 19 раз, остальные по 37, то есть примерно вдвое меньше. Вероятно, причина в том, что обоим нужна вилка 0 в качестве первой, и они делят её между собой, пока остальные такого общего узкого места не имеют (гипотеза, отдельно не проверялась).
- **limited** справедлив (20–21 приём у каждого), но почти не распараллеливает еду (в среднем 1.02 едока, всего 102). Вероятно, из-за паузы между вилками: все четверо за столом берут левую вилку и строят цепочку ожидания, в которой есть только один, кто может есть, а остальные получают вилки по очереди (гипотеза, отдельно не проверялась).
- Компромисс: справедливость против пропускной способности. Нумерация вилок быстрее, но неравномерна, а ограничение мест ровнее, но медленнее.

## Контрольные вопросы

**1. Почему упорядочивание захвата ресурсов исключает deadlock?**
Пронумеруем ресурсы и потребуем, чтобы каждый поток брал их только по возрастанию номеров. Тогда поток, который держит ресурсы и ждёт ресурс с номером r, держит только ресурсы с номерами **меньше** r. Допустим, цикл ожидания всё же возник: T1 держит ресурс a₁ и ждёт a₂ (его держит T2), T2 держит a₂ и ждёт a₃, …, Tₖ держит aₖ и ждёт a₁. Тогда a₁ < a₂ < … < aₖ < a₁, то есть a₁ < a₁, что невозможно. Пример на двух замках: A = 1, B = 2. Если T1 держит 1 и ждёт 2, то T2, держащий 2, не может ждать 1, потому что по правилу он взял бы 1 раньше 2. Так нарушается четвёртое условие Коффмана (циклическое ожидание), поэтому deadlock невозможен. В философах это видно на примере философа 4, который берёт вилку 0 раньше вилки 4.

**2. Почему алгоритм банкира редко применяется в универсальных ОС?**
- Нужно знать **максимальную потребность** (Max) каждого процесса заранее, а в универсальной ОС программа обычно не знает, сколько ресурсов запросит.
- Требуются фиксированное число процессов и ресурсов и гарантия, что процесс вернёт ресурсы за конечное время, чего ОС общего назначения обещать не может.
- Дорогая проверка: на каждый запрос нужен алгоритм безопасности. Он делает не более n проходов по n процессам, в каждом сравнивает векторы из m чисел, то есть порядка n² · m операций. В нашем примере n = 5, m = 3, значит 5² · 3 = 75 сравнений на запрос; для тысяч процессов это дорого.
- Осторожность: банкир отклоняет запросы, которые приводят к небезопасному состоянию (как P0 (0,2,0) выше), даже если deadlock так и не наступил бы, и тем самым занижает использование ресурсов.
- Поэтому в универсальных ОС чаще не защищаются от взаимоблокировок вообще (страусиный алгоритм), либо применяют упорядочивание захвата (в ядре Linux, в коде приложений), таймауты, а также обнаружение с последующим завершением процесса.
